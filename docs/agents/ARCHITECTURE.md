# Видимая научная часть, скрытая обвязка

[Начало](README.md)

## Четыре файла, которые имеет смысл читать человеку

```text
research/
  method.py       извлечь признаки → вычислить logit → сравнить вероятность с порогом
  features.py     состояния выбранных слоёв → последняя немаскированная позиция
  predictor.py    Linear либо небольшой MLP, построенные явно
  train.py        признаки + метки → BCE → обновление весов головы
```

В текущем ядре форма признаков `[B,K,D]`: B задач, K выбранных состояний слоёв,
D координат каждого состояния. Голова разворачивает последние две оси в `[B,K*D]`
и возвращает `[B,1]`; `method.py` убирает последнюю единичную ось. Список слоёв и его порядок — часть определения признаков.
Функции можно импортировать из будущего solution; не копировать формулы.

`features.py` получает **уже загруженную LLM** и токенизированный батч, но само
обращение `llm(..., output_hidden_states=True)` остаётся видимым.
`predictor.py` не загружает pickle и не скрывает архитектуру за библиотечным объектом.
`train.py` получает только обучающую выборку признаков; разделение данных выполняется раньше.

В репозитории остаются прежние baseline. Новый код не объявляется лучшим методом:
он задаёт прозрачный интерфейс, который предстоит подключить к данным и проверить на реальной LLM.
Не создаём третью заведомо неработающую папку в `solutions/`.

## Что агент реализует в обвязке по мере необходимости

Загрузчик данных, проверка схемы, чтение весов, перенос на устройство, файловый кеш,
цикл батчей, журнал, упаковка. Создавать отдельный helper только когда появился реальный
второй пользователь/осмысленная ответственность. Не строить заранее framework.

Будущий путь отправки:

```text
solution.are_robust(model_id, problems)
  → обвязка загружает именно разрешённый checkpoint/tokenizer/голову
  → токенизация по сохранённому описанию
  → research.method.predict(...)
  → list[bool] в исходном порядке
```

При упаковке включить пакет `research` и нужную обвязку в ZIP; проверить импорт в чистом
каталоге, без репозитория в PYTHONPATH. Датасеты, MEMORY, .codex и .agents в отправку не входят.

## Что нельзя спрятать как «не влияющее на результат»

Шаблон промпта, токенизатор, предел длины, сторона обрезания, padding и маски,
checkpoint/revision, режим eval, dtype, индексы hidden_states, точка нормировки,
способ объединения токенов/слоёв, порог и порядок признаков влияют на вычисление.
Файловый путь обычно не влияет; содержимое файла весов влияет.

Поэтому их значения записываются в небольшую карточку/manifest (описание запуска).
Нельзя молча менять dtype или урезать длину при OOM и называть это тем же опытом.
Уменьшение батча тоже записывается: математический замысел прежний, численные результаты
не обязаны совпасть побитно. Обучение и применение используют одну функцию извлечения.

## Кеш и пять направлений

Ветки 1–3 производят признаки с одинаковыми ID задач и split_id; ветка 4 потребляет их;
ветка 5 задаёт разбиение и контроль качества ещё до первого большого запуска.
Минимальный ключ кеша включает code_sha извлечения, хеш данных/семейств, checkpoint revision,
tokenizer revision, шаблон промпта, слои, pooling, маску, длины, dtype и настройки генерации.
Нормировка/PCA, обучаемые по данным, имеют ещё ID обучающего фолда: один fitted scaler
для всего датасета недопустим. Большие массивы вне Git; manifest и контрольные суммы — в журнале.

Пример: одинаковые размеры `[B,K,D]` не позволяют соединить массивы по номеру строки.
Сначала проверить совпадение ID и вернуть нужный порядок; иначе голова учится на чужих метках.
