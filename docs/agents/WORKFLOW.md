# От обсуждения до проверенного опыта

[Начало](README.md)

## Один исследовательский цикл

**Вопрос → альтернативы → маленькая различающая проверка → код → тест → опыт →
проверка результата → запись → следующий вопрос.** Успех цикла — надёжный ответ,
включая отрицательный. «Получить 90% любой ценой» не является корректным заданием.

Astra формулирует максимум три объяснения и наблюдение, которое их различит.
При важном выборе можно дать двум агентам независимо предложить объяснение и
контрпример. Они сначала получают факты, а не чужой вывод. Затем один обмен возражениями;
Astra выбирает проверку. Длинные дебаты прекращаются, когда нужна новая информация.
Согласие агентов не заменяет данные; не сохранять его как подтверждённую гипотезу.

Карточка опыта включает гипотезу, baseline (с чем сравниваем), единицу данных,
разбиение, главный показатель, изменяемые параметры, лимиты, ожидаемые артефакты,
условия остановки и то, какой исход опровергнет предположение.
Новый способ разделения/показатель после просмотра результата означает новый опыт.

## Как пятеро работают параллельно

Направление 1: переформулировки и изменение состояний, одна группа на исходную задачу.
Направление 2: состояния и изменения по глубине слоёв.
Направление 3: вероятности токенов во время ответа и их изменения.
Направление 4: сначала общий контракт признаков, тесты/простая голова на искусственных
данных; потом сравнение голов на первых кешах, а не ожидание полного окончания 1–3.
Направление 5: с первого дня схема/дубли/семейства/разбиение и простые контрольные
методы; потом независимая проверка выводов. Это обязанность до запуска, не уборка после.

У каждого направления отдельная ветка и git worktree — отдельная рабочая папка,
использующая общую Git-историю. Подагент не получает автоматически изолированную папку
только от слова «подагент»: изоляцию создают явно. Один владелец общих интерфейсов,
один интегратор STATE/DECISIONS; предложения остальных — отдельные handoff-файлы.
На одну доступную GPU одновременно одна тяжёлая работа по умолчанию.

## Задание подагенту

```text
Вопрос/цель:
Входные файлы и исходный commit:
Разрешённые файлы для записи / рабочая папка / ветка:
Не менять:
Критерии приёмки и команды проверки:
Разрешённые ресурсы и предел попыток:
Вернуть: вывод, diff/пути, тесты с фактическим исходом, риски, блокеры.
Не создавать новых подагентов.
```

Узкий поиск — Luna; реализация/тесты — Terra; научная проверка — Astra.
Не отдавать всю историю беседы каждому: несколько релевантных файлов и точный вопрос.
После ответа координатор читает diff и свидетельства, а не пересказывает авторское «готово».

## Прежде чем оставить агента с видеокартой

Нужно один раз установить фактические возможности компьютера и разрешения:
GPU/VRAM, место на диске, доступные checkpoints, версии библиотек, сеть, разрешённый
каталог результатов. Агент не должен угадывать их из прошлой переписки.

Затем человек согласует ограниченную серию: какие опыты, максимум запусков/времени,
какие данные/модели/параметры, разрешены ли платные API, когда остановиться.
В образце plan.json запуск **не разрешён**. Никаких бессрочных «оптимизируй, пока не станет хорошо».

`run_experiment.py` требует согласованную и закоммиченную карточку, чистое дерево,
записывает code_sha и plan_sha256, выполняет argv без shell, ограничивает время,
не перезаписывает ID и блокирует другой опыт того же репозитория во всех его worktrees.
Запись `succeeded` означает только завершение команды с exit code 0, не научную достоверность.
GPU-метрики/качество проверяет отдельный review. JSON-согласование — журнал разрешения,
не криптографическая подпись человека: агент не вправе выдавать своё имя за согласие пользователя.

Ограничения runner: не контролирует API-кредиты и VRAM сам; не запрещает сеть;
не заменяет OS sandbox/очередь; lock не общий для независимых clones/компьютеров.
При аварийном выключении может остаться lock/незавершённая запись. Сначала проверить
процесс и логи, потом вручную отметить interrupted; никогда не удалять lock вслепую.
Windows-ветка остановки дерева процессов требует локальной проверки на Windows.

Для длинной работы Codex поддерживает `/goal` с критерием завершения; это функция
установленного клиента. Она не означает, что этот чат получил доступ к твоей GPU.
Смена вопроса, новая серия сверх бюджета или новые права возвращаются к человеку.

## Git: опыт нельзя потерять после squash

1. Коммит исходников и карточки: `exp(depth): prepare E-depth-001`.
2. Запуск из чистого дерева. В записи автоматически фиксируется этот commit.
3. Проверка файлов/метрик; краткий человеческий вывод в отдельном report.md.
4. Коммит записи даже при ошибке: `result(E-depth-001): failed — invalid mask`.
   В body: что проверено; что получено; где доказательства; что не проверялось.
5. Следующий опыт только после result-коммита. Тесты внутри одной правки группируются
   в один итоговый коммит; не нужен коммит после каждого чтения/команды.

Runner намеренно не делает `git add .`, не коммитит и не пушит сам: координатор сначала
проверяет, что журнал не содержит закрытых данных. При отсутствии прав коммита
зафиксировать блокер и не начинать следующую серию. Для зависшего опыта на возобновлении
создать запись об interruption и новый run_id, не дописывать выдуманный успешный результат.

В main переносится проверенная реализация, при желании одним squash-коммитом.
Но сначала сохранить исходную исследовательскую ветку либо archive-tag и доступ к её
коммитам, включить все журналы попыток/ссылки в перенос. «Лучший коммит» не позволяет
удалить неудобные результаты: это испортит оценку числа попыток и воспроизводимость.
Force-push общей ветки, удаление чужих веток, автоматическая отправка на Codabench запрещены
без отдельного согласования. При параллельном изменении main интегрировать заново, не затереть.

## Как признать результат полезным

Показать число независимых задач, метрику и её неопределённость, baseline на том же
разбиении, число просмотренных вариантов, расходы и технические отказы.
Убрать группу признаков и переобучить — отдельный опыт на тех же разбиениях.
Проверка на случайных метках перемешивает метки **по группам задач**, затем запускает
весь подбор заново; сравнивать с уровнем дисбаланса классов, не автоматически с 50%.

Bootstrap — многократная перевыборка задач для оценки разброса — тоже по независимым
семействам, не по всем перефразам как будто это разные задачи. Финальный holdout (отложенный
набор) открывать только по отдельному решению после выбора метода. Эти правила — проектный
протокол; согласовать конкретную схему с фактическим датасетом и актуальными правилами AIMO.
