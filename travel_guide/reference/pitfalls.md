# Несовпадения исходников и ловушки

[Начало](../README.md). Это наблюдения о коммите `e46be92387081cfb8edf275e573fec7884eb9f32`, не утверждения о текущем сервере организаторов. Рабочие исходники guide не меняет.

## 1. Импортёр создаёт не тот problem, который читает ingestion

[`convert_rows`](../../scripts/import_hf_dataset.py) записывает:

```python
{"id": case_id, "model_id": model_id,
 "problem": {"original_problem": text, "permutation_type": [...]}}
```

Но [`load_cases`](../../components/ingestion_program/ingestion.py) требует непустой `str` в `problem`. Поэтому прямой импорт и запуск README в этом snapshot могут завершиться `invalid problem` **до вызова твоего метода**. Это не исправляется перестановкой тензоров или установкой Transformers.

Для локальной разработки есть явный конвертер, который извлекает `original_problem`, сохраняет ID/порядок и пишет **новый файл**, не меняя исходный и не читая метки:

```bash
python scripts/import_hf_dataset.py
python travel_guide/tools/normalize_cases.py data/val-sample/input/cases.jsonl data/val-sample-text/input/cases.jsonl
python scripts/run_local.py solutions/always-true --input-dir data/val-sample-text/input --reference-dir data/val-sample/reference
```

Первой команде нужны настроенное окружение и доступ к датасету; две следующие не загружают LLM. Конвертер откажется перезаписывать существующий выход. Это обход несовпадения **локальных файлов**, а не изменение серверного формата или повод передавать в `are_robust` словари.

## 2. Часть contract-тестов относится к прежнему поведению

[`test_ingestion_contract.py`](../../tests/test_ingestion_contract.py) содержит тест, ожидающий отказа из-за старой аннотации `list[Problem]`, и тест, подающий словарь в поле `problem`. В текущем ingestion аннотации не проверяются, а словарь отвергается. Поэтому по коду ожидаемы один failure и одна error при запуске этих трёх тестов:

```bash
python -m unittest discover -s tests -p test_ingestion_contract.py -v
```

Guide не ослабляет тесты ради зелёного отчёта и не меняет контракт. Отдельные проверки guide покрывают фактическое текущее поведение. Аннотации в своём solution всё равно оставляй документированные: серверная версия evaluator может отличаться.

## 3. `build.py all` требует отсутствующие организаторские шаблоны

[`build.py`](../../scripts/build.py) после сборки компонентов обращается к `task/task.embedded.yaml`, затем к ресурсам `competition/`. В исходном дереве этого форка соответствующих папок нет. Для solution ZIP используй `components`, как показано [в маршруте](../route/04-your-method.md). Не нужно восстанавливать инфраструктуру проведения всего соревнования, чтобы отправить один метод.

## 4. Валидный ответ ещё не означает работу задуманного метода

Оба сложных baseline при отсутствии подходящего артефакта возвращают все `False`. Это даёт coverage 1. Но malformed существующий артефакт не обязан перейти в fallback: его загрузчик может выбросить исключение. Не считай молчание evaluator доказательством, что загрузились нужные веса.

У probe generic `.pkl` может быть найден независимо от запрошенного имени; затем `_encode_problem` загружает **`artifact.model_id`**. Проверки равенства request и checkpoint, аналогичной uncertainty-path, здесь нет. Перед работой с несколькими моделями это нужно согласовать, а не доверять одному размеру hidden state.

`_load_model` у probe вызывается на каждой задаче; у uncertainty — один раз на вызов для модели. Первое — заметная кандидатура для оптимизации. Однако guide не выдаёт статический анализ за измеренное время или расход VRAM.

## 5. Оценка метода и исследовательские выводы

Подбор uncertainty оптимизирует balanced accuracy, внешний evaluator — обычную accuracy. При дисбалансе классов оптимальные пороги могут отличаться. Менять критерий можно, но результат нужно проверять отдельно от данных подбора.

OOF исключает обучение конкретного estimator на собственной validation-строке, но подбор многих моделей и порога по тем же OOF-прогнозам всё равно использует их метки. Для независимой финальной оценки нужен отложенный набор групп или вложенная проверка. Группировка по точному тексту защищает от точных повторов, но сама по себе не объединяет разные перефразировки одной исходной задачи.

Низкая энтропия не доказывает правильность рассуждения: модель может ошибаться уверенно. Хорошая probe-точность показывает предсказательную связь представления с меткой, а не автоматически причинный механизм устойчивости. Эти ограничения важны, если ты затем превращаешь конкурсный метод в интерпретационное исследование.

## 6. Окружение и доступ к данным

README называет выборку public, а импортёр содержит обработку авторизации и комментарии о private data. По одному тексту репозитория нельзя надёжно установить текущие права доступа к Hugging Face. При 401/403 проверяй доступ своего аккаунта; не вставляй токен в код, ZIP или commit.

CPU-примеры guide не запускают 8B checkpoint. Реальный inference требует локальных весов, подходящих версий библиотек и достаточной памяти. Уменьшение batch size помогает не всем видам расхода памяти: веса модели от этого меньше не становятся. Изменение generation config также может сделать старый регрессор статистически неподходящим.
