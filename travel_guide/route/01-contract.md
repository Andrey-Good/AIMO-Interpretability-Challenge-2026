# 1. Контракт и путь одной задачи

[Начало](../README.md) · Далее: [representation probe](02-probe.md)

## Что именно ты предсказываешь

На вход приходит математическая задача и идентификатор модели. На выходе требуется не ответ на задачу, а **прогноз устойчивости поведения этой модели**: `True` или `False`. Интуиция устойчивости — насколько поведение сохраняется при изменениях формулировки. Это не то же самое, что правильность одного ответа. Точное правило формирования метки берётся из данных и правил организаторов; ingestion и scoring его не вычисляют.

У этого проекта две разные модели. **LLM** читает задачу и даёт внутренние сигналы. **Твой предсказатель** превращает сигналы в оценку устойчивости. В существующих решениях LLM во время отправки не дообучается.

## Самое маленькое решение

В [оригинальном `always-true/solution.py`](../../solutions/always-true/solution.py) метод возвращает `True` для каждой задачи. По сути:

```python
# Иллюстрация контракта, а не улучшенный метод.
def are_robust(model_id: str, problems: list[str]) -> list[bool]:
    return [True for _ in problems]
```

`model_id` относится ко всему списку; `problems[i]` — обычная строка. На позиции `i` ответа должен стоять прогноз для неё же. Метки и идентификаторы примеров в эту функцию не передаются. Если пришло 100 задач, это **не означает**, что 100 текстов нужно одновременно класть на GPU: внутри можно обрабатывать их по одному или небольшими батчами.

Контракт проверяется строго: именно `list`, правильная длина, именно Python `bool`. `np.bool_`, `torch.Tensor`, числа `0/1` и генератор не подходят. При выходе из NumPy/PyTorch используй явное преобразование, например `[bool(x) for x in decisions]`.

## Один проход через файлы

```text
scripts/run_local.py
    ├─ запускает components/ingestion_program/ingestion.py
    │    cases.jsonl → load_cases → load_solution → solution.are_robust
    │                                              ↓
    │                                    predictions.jsonl
    └─ запускает components/scoring_program/scoring.py
         labels.jsonl + predictions.jsonl → scores.json
```

[`run_local.py`](../../scripts/run_local.py) создаёт временные каталоги и запускает два отдельных Python-процесса. После печати оценки временные результаты удаляются. Это оболочка для проверки, не место разработки исследовательского метода.

В текущем [`ingestion.py`](../../components/ingestion_program/ingestion.py) допустимая строка входного JSONL выглядит так:

```json
{"id":"example-1","model_id":"example/model","problem":"Find all integers n ..."}
```

JSONL — несколько самостоятельных JSON-объектов, по одному на строку. `load_cases` проверяет поля и уникальность `id`. `load_solution` загружает `solution.py` из указанной папки. В текущем коде проверяется наличие вызываемой функции, **не её аннотации типов**, несмотря на формулировку исходного README.

Затем `_run` группирует записи по `model_id`, сохраняя исходные индексы. Например, записи `A1, B1, A2` превращаются в вызовы для `[A1, A2]` и `[B1]`; выход снова записывается в порядке `A1, B1, A2`. Поэтому внутреннее переупорядочивание твоих задач без обратной перестановки испортит оценку.

**Ошибка одного элемента ответа делает невалидным весь вызов для данной модели.** Если для двух задач вернулось `[True, 0]`, ни одна из двух не считается корректно обработанной. Исключение внутри `are_robust` также перехватывается без traceback в результатах. Но ошибка импорта `solution.py` или самого входного файла возникает раньше этого перехвата и может остановить ingestion целиком. [Тот самый блок с комментариями](../annotated/ingestion_core.py).

## Что означает результат

Ingestion записывает, например:

```json
{"id":"example-1","is_robust":false,"valid":true}
```

`is_robust=False` — полноценный прогноз. `valid=False` — техническая неудача, а не прогноз неустойчивости. Эти два поля нельзя смешивать.

В [`scoring.py::compute_scores`](../../components/scoring_program/scoring.py) считаются:

$$
\mathrm{accuracy}=\frac{\text{верные валидные прогнозы}}{\text{все эталонные примеры}},\qquad
\mathrm{coverage}=\frac{\text{валидные прогнозы}}{\text{все эталонные примеры}}.
$$

При 10 примерах, 8 валидных и 6 верных получаются `accuracy=0.6`, `coverage=0.8`, а **не** `6/8`. Невалидные ответы не позволяют искусственно улучшить accuracy. `invalid_predictions` дополнительно учитывает ошибки структуры: повреждённые записи, повторные и лишние ID. Поэтому в общем случае это не просто число пропущенных примеров.

Сначала проверяй `coverage == 1` и отсутствие invalid, затем качество классификации. И даже идеальная coverage не доказывает работу нейросети: оба сложных baseline могут вернуть все `False`, если нужного артефакта нет.

### Проверка понимания

Почему решение, всегда возвращающее `True`, иногда лучше случайного? Почему нельзя вернуть правильные ответы, но отсортированные по уверенности?

<details><summary>Ответ</summary>

Точность такого решения равна доле устойчивых примеров, которая не обязана быть 50%. Позиция в возвращаемом списке связывает прогноз с задачей; сортировка без восстановления порядка нарушает эту связь.

</details>
